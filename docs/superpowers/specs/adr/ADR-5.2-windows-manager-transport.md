# ADR-5.2 — Windows local manager transport and authentication contract

- Status: ACCEPTED (design decision, 2026-11-17)
- Context: The design (§1, §15.4) requires a privileged local target manager on the Windows control-plane machine with an authenticated, replay-safe protocol. The worker, API and manager run on the same Windows host for LOCAL_WINDOWS.
- Decision:
  - **Transport:** one fixed named pipe, `\\.\pipe\nimbusops-manager-v1`, created by the manager service. DACL on the pipe grants only: the worker's dedicated service account SID (read/write), SYSTEM and Administrators. Anonymous and Everyone are explicitly denied. The manager validates the peer SID of every connecting client via `GetNamedPipeClientProcessId`/pipe impersonation and rejects unexpected accounts (fail closed).
  - **Message framing:** length-prefixed UTF-8 JSON, max 64 KiB per frame, request/response pairs with `request_id` matching §15.4 fields (protocol_version=1, job_id, dispatch_id, intent_hash, machine binding, ownership generation, expected credential/revocation revisions).
  - **Authentication model:** pipe SID + peer process check is the transport identity; every ADMIT/START_ACTION request additionally carries the backend-issued admission receipt token (random 256-bit, single dispatch, stored hashed server-side). Receipt TTL is a availability bound, never a closure semantic: an ADMITTED, un-CLOSED dispatch forbids retry/release until the manager proves terminal state (design §15.1), regardless of receipt expiry. The manager validates the receipt against the backend over its own authenticated channel before the first privileged effect; the backend ADMIT CAS and every START_ACTION recheck serialize on the exact `revocation_revision` and cancellation state, and close OPEN attempts on revoke/cancel (§15.1/§15.2). Field presence alone is not the predicate.
  - **Peer identity verification path:** the manager impersonates the connecting client over the named pipe and reads the impersonated thread token's user SID (or equivalently resolves the client PID via `GetNamedPipeClientProcessId` to its process token user SID); it compares against the allowlisted worker service-account SID and rejects all others fail-closed. A PID alone is never treated as identity.
  - **Replay/fencing:** manager journal deduplicates by dispatch_id; a repeated ADMIT with the same dispatch returns the existing journal status; a different intent_hash for the same dispatch is rejected. CLOSED attempts are refused even with a valid receipt.
  - **Config:** manager location/installation ID pinned in server connection config (file reference, no secrets in DB); the worker discovers the pipe only from that pinned config — no auto-discovery of arbitrary pipes.
- Consequences:
  - No secrets transit argv or environment; the grant/exchange flow for LOCAL_WINDOWS is unnecessary (no remote cloud transport) — the manager obtains capabilities directly over the authenticated pipe.
  - Peer-SID validation requires the worker and manager run under distinct dedicated accounts; running both as the same account is a setup-required misconfiguration.
  - Windows named pipe behavior (impersonation, SID checks, reconnect races) must be exercised on a disposable Windows host (G7) before real acceptance; mocks cover framing/dedup logic only.
- Enforcement: D6W tests cover DACL construction, peer-SID rejection, receipt validation, journal dedup and closed-attempt refusal; fixtures frozen in D0.
